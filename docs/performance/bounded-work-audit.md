# Remaining work bounds for the nine-millisecond goal

This source audit covers candidate `3ad9f87`. It identifies growth paths; it is **not** a new CPU profile or evidence that a particular unmeasured operation breaches nine milliseconds. The [completion ledger](nine-ms-goal.md) and operation-attributed production samples remain authoritative for performance gates. Proposed architecture changes below have not been implemented.

## Existing bounds and remaining whole-input work

| Surface | Current bound / implementation | Remaining growth path |
| --- | --- | --- |
| HTTP envelopes | `index.ts` and `services/http.ts` enforce 64 KiB, including streamed bodies | A byte limit does not establish CPU for parsing/schema failures at that bound; account/database size is independent of request bytes |
| Compact sync status | `repositories/syncStatusRead.ts` projects six queries and omits historical interval JSON when counts exist | All history summaries, all roster choices and all pending records still arrive in one response; legacy missing counts still parse full historical blobs |
| Generic reads | `repositories/database.ts` selects operation-specific tables | Each selected table is read in full; prior scheduling runs/assignments and unrelated users can grow independently of the visible view |
| Insights | `domain/insights.ts` normalizes availability once per volunteer/day | Every grid cell filters eligible volunteers and returns full volunteer records; payload grows with grid membership as well as roster size |
| Center proposals | `handlers/candidates.ts` computes coverage for every visible candidate | `domain/candidates.ts` filters the recurring interval array for each eligible volunteer, repeated for each candidate |
| Schedule preview / publish | `domain/scheduler.ts` shares normalized availability within one calculation | All future sessions and volunteers are considered in one invocation; conflict checks traverse assignments and sessions; publish also creates the whole output |
| Ordinary mutations | `api/dispatch.ts` reads the snapshot, clones it, handles the command and commits | Most writes lack an operation table projection; commit computes table differences, and relevant writes also materialize the full prepared schedule inline |
| Source fetch | `WhenIsGoodClient.ts` caps source bytes at 2 MiB; unchanged fingerprint exits before parsing | Stream accumulation, text decoding, hashing and saving artifacts still process the whole source in one stage |
| Queue parse | `synchronizationJobs.ts` gives parsing a separate invocation | `repositories/synchronizationJobs.ts` joins every source artifact; `parseWhenIsGood` parses the entire body and serializes all parsed participants |
| Queue prepare / reconcile / commit | Durable phases, revision fences and idempotent final commit exist | Artifact chunks are storage chunks, not computation chunks: each stage joins all parts, parses the whole JSON and prepares/applies the whole plan |
| Recovery | Individual recovery/expiry selections use bounded counts | Total artifact deletion per terminal job and the size of each selected job remain separate concerns; SQL time is not itself Worker CPU proof |

## Changes to propose if the measured gates require them

1. **Narrow existing queries and reuse indexes before adding protocols.** Select the current completed scheduling run and its assignments in the repository instead of hydrating all historical runs. Build one recurring-availability index for a proposal read, preserving interval normalization and volunteer ordering through the shared domain owner. These are smaller implementation candidates, but need behavioral tests and production measurements; source inspection alone does not justify a CPU prediction.
2. **Page collections without dropping records.** Separate history pages, roster search/pages and pending records from the small status header. Use stable keyset ordering and revision-aware continuation, with a typed reload/restart when consistency cannot be preserved. Do not use a silent LIMIT on the existing response: the user still needs every history record and linking choice. This changes the API and UI and should be reviewed as a design change before implementation.
3. **Make Queue stages bounded by work, not only phase.** Persist a cursor and partial parser/reconciliation state. Read only the next bounded artifact/participant slice, stage results durably, and enqueue the continuation. A parser continuation must preserve native and embedded-JSON source formats, cross-chunk strings/entities/UTF-8 boundaries and strict rejection of malformed nonempty availability. Global duplicate identity counts and matching indexes must be completed before reconciliation. Chunking raw text alone does not solve this.
4. **Keep one fenced, idempotent publication boundary.** Incremental computation must not expose partial availability. A final small commit would publish a prepared generation; staged rows would be read only after that generation becomes current. This is a larger storage/model change, requiring a design proposal, migration approval and concurrency/retry tests. Splitting the existing final SQL transaction across deliveries would violate the current atomicity contract.
5. **Treat writer projections as command contracts.** A narrow mutation load must define exactly which tables it owns and which current-authority, conflict and revision checks it needs. The current whole-snapshot diff must not interpret omitted tables as deletions. If prepared schedule work moves to a job, define whether reads wait, show a stale revision or return a pending state; preserve the existing fail-closed fence until the replacement semantics are approved.
6. **Consider browser computation for advisory work.** Insights, coverage and schedule preview can potentially use a revision-bound, authorized, paginated input projection and the shared domain algorithms in the browser. Publishing or confirming remains server-authoritative; blindly trusting a client-computed schedule would weaken current conflict and eligibility checks. This is an architecture proposal, not an implementation authorized by a read-only release trial.

None of these establishes a universal nine-millisecond bound by itself. Each needs explicit supported input limits or bounded continuations, preserved semantics, and repeated production CPU at those bounds. Rust/Wasm does not remove full snapshot hydration, JSON transfer, output growth or cross-stage atomicity requirements; consider it only if production profiling isolates a computational routine that warrants it.

## Order of evidence

First finish the approved compact-candidate read gates. A measured failure chooses the next narrow experiment; do not change multiple remaining paths based on local timing forecasts. Then cover volunteer reads with an authorized volunteer, and obtain concrete approval for any production mutation/changed-source test. Revisit the larger designs above if representative or growth-bound measurements cannot satisfy the gate with ordinary projections and shared indexes. The overall goal remains open throughout.
