Measured on 2026-09-22 while verifying an unrelated production change, and a failure mode the classification must cover: a slow read does not merely breach a threshold, it stops the application loading at all. A devtools capture of the deployed client showed a `POST .../exec` lasting **18.2 s** returning 302, whose follow-up `GET .../echo?user_content_key=...` returned **404** carrying a Google Drive HTML page — "Sorry, unable to open the file at this time." A control request in the same page load returned 200 with JSON after **4.7 s**. So the Apps Script result handoff fails when the execution is slow, and the client, which cannot parse HTML, reports it as an invalid response and renders a fallback error instead of the section. Every execution in the Apps Script Executions view read "Completed" throughout, so server-side status does not surface this at all: the probe's failure classification has to work from the client's own view, and must separate this handoff failure from an upstream or cold-start cause
