- [ ] 10.27 Point the notification mailer at a service the manifest actually authorizes: `src/server/appsscript.json` declares `https://www.googleapis.com/auth/script.send_mail`, which authorizes `MailApp`, but the runtime took its mailer from `GmailApp` (`src/server/runtime.ts`), and `GmailApp.sendEmail` requires one of the Gmail scopes instead. Every notification attempt therefore throws `Exception: Specified permissions are not sufficient to perform the action. Required permissions: (https://mail.google.com/ || https://www.googleapis.com/auth/gmail.send || https://www.googleapis.com/auth/gmail.compose || https://www.googleapis.com/auth/gmail.modify || https://www.googleapis.com/auth/gmail.addons.current.action.compose)`, and `deliverPersisted` catches it into the in-memory `failed` record described in 10.26 — so no email is sent and nothing anywhere records why. Measured on 2026-09-22 by running a reviewed editor probe in the bound project: `ADMINISTRATOR_RECIPIENTS` held a valid one-element JSON array whose single address passed an email-shape check, the bare-global and `globalThis` mailer lookups were both truthy and agreed, and the send still returned `sent: false` with that exception. The two candidate causes that would not need a scope change — an empty or unparseable recipient property, and an absent `GmailApp` — are therefore eliminated and the scope gap is confirmed. This is why the administrator cancellation email left no Sent mail during the 2026-09-21 acceptance, and it also means 5.5's administrator cancellation-result email cannot deliver in production as deployed, and that the malformed-recipient hazard documented in `docs/operations.md` is currently indistinguishable from this blanket failure. The fix is to read `MailApp` in the runtime instead of `GmailApp`, implemented in `resolveMailer` (`src/server/runtime.ts`) with a regression that fails when the resolver is pointed back at `GmailApp`. Keeping `GmailApp` and declaring a Gmail scope is **not** an equivalent alternative: the reference documents that every `GmailApp` method requires the full-mailbox `https://mail.google.com/` scope, not the narrow `https://www.googleapis.com/auth/gmail.send` that the thrown message also lists, so that route would ask the deploying account to hand a web app which executes as them for anonymous callers read, compose, send and delete access to the entire mailbox. `MailApp.sendEmail` is authorized by the already-declared `https://www.googleapis.com/auth/script.send_mail`, so the fix needs no new consent, no manifest change, and no scope escalation — confirmed in the bound project on 2026-09-22, when a reviewed probe's `MailApp.sendEmail` call succeeded against the already-granted scopes and the message arrived, while its `GmailApp` call had thrown the permission error above on the same day. That is the same project, the same account, and the same call shape the runtime uses, so the only thing separating the deployed app from working delivery is the deployment itself. It is inert until a server deployment, which needs its own approval and a workbook snapshot, and delivery still has to be confirmed by observing the message arrive rather than by reading any record, because the status is in memory only (10.26). Prevention, and a caveat about it: `scripts/audit-server-bundle.mjs` already rejects unsupported globals in the emitted bundle by AST, and a sibling check that the declared `oauthScopes` cover every service the bundle reaches would have caught the original defect — which read the service inline as `globalThis.GmailApp`. Any such check must therefore treat a service reached through a parameter as reachable, or the runtime must read the service at the `globalThis` boundary. Nothing currently checks that the manifest and the code agree about which services are used, so a naive version of that check would give false confidence. Deployed 2026-09-22 under explicit one-time approval: the guarded deployment pushed `Code.js` and `appsscript.json` and moved the pinned deployment from version 25 to version 26, with zero issues and the write-disabled posture holding; a restricted pre-deployment export was taken and its structure verified against `src/server/workbook/schema.ts`, and the live `WRITE_ENABLED` was confirmed false by the owner before the push, since no local artifact can establish it.
