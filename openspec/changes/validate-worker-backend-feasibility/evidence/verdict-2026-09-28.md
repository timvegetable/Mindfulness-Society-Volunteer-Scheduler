# Durable Object topology verdict — 2026-09-28 (no-go as built; the read path is feasible)

Task 3.5's amended contract (`evidence/experiment-contract.md`, amendment
2026-09-27) predeclared the acceptance targets for the isolated topology
(browser → thin gateway Worker → Durable Object → Sheets) before measurement.
This verdict records the measured results against those targets. The 2026-09-27
verdict of the single-Worker topology remains the historical record, with its
percentile corrections in [verdict-addendum-2026-09-27.md](verdict-addendum-2026-09-27.md).

## Topology and deployments

`volunteer-scheduling-staging-host` (Durable Object class `StagingWorkbookHost`,
SQLite migration `v1`, no public route or workers.dev endpoint, Google
credentials on the host only) and `volunteer-scheduling-staging-gateway`
(cross-script binding, streaming forwarder, correlation ids, config-derived
object naming) were deployed under per-deployment approvals on 2026-09-28
(reports in ignored `staging-local/deployment-staging-*.json`). The baseline
staging Worker stayed deployed and unchanged. The benchmark route was enabled
for the campaign by an approved host redeploy and disabled again by the final
approved host redeploy (verified: `POST /benchmark/schedule-preview` → 404
`NOT_FOUND` with zero Sheets reads afterwards; reads still serve).

## What the topology proved

* The **read path is feasible on this free topology end to end**: gateway CPU
  ≤ 2.7 ms, object read CPU in the tens of milliseconds, read wall p99 ≤ 1.0 s
  on both fixtures at four-way concurrency, zero post-fix unexpected failures,
  memory 55 MiB, correct denials on both routes, unchanged workbook.
* The gateway/object split behaves as designed: streamed responses, exact CORS
  allowlisting, binding-failure envelopes, request-local counters, no object
  storage writes, and credentials only on the host.
* The staging benchmark endpoint works as specified (default-disabled 404,
  fresh administrator, one 7-tab batch, real handler with the authenticated
  principal) and measured the preview honestly.

## Why the verdict is no-go as built

The predeclared preview targets fail on the larger fixture, and not marginally:

1. **Preview CPU ≈ 7.5–12 s per request** against the predeclared ≤ 3 s (warm
   p99) / ≤ 5 s (every request) — the same synchronous computation the 2026-09-27
   verdict measured at 6.9 s on 3–4 vCPUs, now on a single vCPU-class isolate.
   The Durable Object removed the 10 ms CPU *cap*; it did not reduce the
   computation's cost.
2. **Preview wall ≈ 11 s sustained (p99)** against the predeclared ≤ 5 s, and
   the predeclared four-way preview burst exceeded the platform's per-request
   wall cap: four concurrent larger previews serialize on the single isolate
   and the platform killed ten requests at ~37 s (gateway 503, no correlation
   id, zero reads).
3. The larger preview's burst 429s (browser-probe reads outside the shared
   ledger + burst adjacency) leave the zero-429 gate unmet for that run.

By the contract's own rule — thresholds are never adjusted after results, and
an unmet, undemonstrated-repairable threshold records **no-go** — this topology
is **no-go for production migration as built**. This does not reverse the
positive findings: the read path meets every predeclared target, which is
exactly the evidence `serve-primary-reads-from-worker` needs, and the preview
stays with its existing server until a demonstrably faster computation (the
profiled scheduling/assembly path) passes the same workloads.

## Unresolved conditions carried forward

* **Billable duration** is not published by the DO datasets used here; it stays
  unresolved (the duration gate was therefore evaluated by wall-clock-derived
  estimates only and is not claimed as met).
* **DO per-request CPU quantiles** are not published; the object CPU gate was
  evaluated from per-minute aggregate sums plus wall evidence (labelled), and
  the preview CPU figure is corroborated by the sequential sustained phase.
* The **~120-attempt overage** of the predeclared campaign cap is a recorded
  deviation with its cause (credential-refresh probe sessions).
* A failed JWKS load still gates concurrent retries for
  `minReloadIntervalMs` (the anti-storm rule); a burst that begins with a
  failed load can lose members (observed as the four attributed
  insights-burst failures). The in-flight-join fix removed the concurrent-cold
  failure mode; the failed-load window remains by design.
* The browser probes' Sheets reads are outside the shared read ledger; a
  future campaign should pace them through the same ledger.

## Release constraint

This verdict authorizes nothing beyond the experiment: no production
deployment, no production write, no paid plan. The next change
(`serve-primary-reads-from-worker`) inherits the read-path evidence through
its own gates; the preview requires either a demonstrably faster computation
or a different product decision before it can be re-measured against the same
predeclared thresholds.
